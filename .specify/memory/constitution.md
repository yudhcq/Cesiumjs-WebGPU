# CesiumJS WebGPU Renderer Constitution

## Core Principles

### I. 受控 fork（Controlled Fork，NON-NEGOTIABLE）

本项目的实现手段是**在渲染后端层对上游做受控 fork**，而非仅在上游公开 API 之外另建一条旁路。

- **允许**：fork `@cesium/engine`，或以可 rebase 的补丁层（patch layer）形式承载上游改动；
  两种形态等价，选择依据是可升级性与评审成本，并 MUST 在方案产物中记录。
- **MUST 局限在渲染后端层**：GPU 上下文/设备与资源生命周期、着色器编译、管线与绑定状态、
  绘制执行、帧缓冲与呈现。补丁不得越出该层。
- **MUST NOT 改动逻辑层语义**：`Scene` / `Globe` / `QuadtreePrimitive` 瓦片调度 / `Camera` /
  图层体系 / `DrawCommand` 的语义与公开行为一行不改；MUST NOT 重写、旁路或重新实现这些逻辑，
  也 MUST NOT 借私有内部 API 绕过它们。
- **MUST 保持可升级**：MUST 记录上游基线版本、补丁范围（文件与符号清单）、补丁存在理由；
  MUST 提供升级（rebase）演练与验证方式——每次上游升级必须执行"补丁范围审计（仍只落在渲染后端层）
  + 既有全量验证通过"，二者缺一不得合入。
- 上游公开 API 与官方扩展点仍是**首选接缝**；只有在公开接缝确实不存在（例如上下文接管、
  绘制执行交接）时才允许进入 fork 层，且每次进入 MUST 在方案产物中说明"为何公开接缝不可用"。
- 补丁 MUST 保持最小：单个改动 MUST 可追溯到一条明确需求；禁止借 fork 顺带重构上游。

**Rationale**：本项目的目标是"用 WebGPU 渲染后端替换渲染后端"，而不是在上游之外再挂一条绘制链路。
替换必须在绘制执行发生的地方完成，才能让影像、模型、大气等既有功能随后端替换自然接入；
而上游在该处没有公开接缝（`Scene.context` 为 `@private`，上游不支持注入外部画布或上下文）。
同时，逻辑层是本项目**不打算承担**的复杂度：一旦逻辑层语义被改动，上游升级即从例行操作退化为重写，
故 fork 必须被边界条款与升级演练严格约束。

### II. 二选一，不同时运行（One Backend at a Time，NON-NEGOTIABLE）

- 渲染后端在**初始化时选定**，选定后整个会话只用这一条路径；同一场景在同一会话内
  MUST NOT 被两条路径同时绘制，MUST NOT 以图层叠加、透明/半透明遮挡、逐帧合成或
  "让其中一次的绘制不可见"等方式让两条路径共存。
- WebGL2 为兜底后端，在其被选定的会话中必须可完整运行；WebGPU MUST NOT 成为唯一可运行路径。
- WebGPU 后端必须先经能力探测（`navigator.gpu` 存在性、adapter/device 请求结果、
  必需特性与限制项如纹理格式与最大纹理尺寸）方可启用；探测失败或超时 MUST 在初始化阶段
  整体切换到 WebGL2 路径并重新初始化，MUST NOT 抛出未捕获错误、MUST NOT 阻塞页面其余部分。
- 路径回退与切换 MUST 是**整体切换**：销毁当前后端并以其对端重建，禁止保留前一条路径的任何
  绘制、状态或图层残留；回退路径本身 MUST 被测试覆盖。
- 上层 API 唯一：同一上层接口在两种后端下渲染结果与行为必须保持一致（视觉等价 + 语义等价）；
  无法消除的差异 MUST 在契约中显式声明并附测试断言。
- 路径选择 MUST 能在配置层或运行时完成，调用方代码 MUST NOT 出现后端分支，
  MUST NOT 直接引用具体后端类型。
- 渲染后端抽象（Backend Abstraction）：上层只依赖抽象接口（资源创建、管线与管线缓存、
  命令编码与提交、帧生命周期）；后端实现不得被上层反向 import。

**Rationale**：CesiumJS 生态必须继续兼容仅有 WebGL2 的设备与浏览器，因此兜底路径必须存在；
但"兜底"不等于"并行"——两条路径同时绘制同一场景会付出双份开销，且永远无法让既有功能
（影像、模型、大气、阴影、后处理）接入新后端。二选一是让"管线替换"成为可实现目标的前置约束。

### III. 可验证渲染（Verifiable Rendering）

- 每项渲染特性必须附带自动化验证：像素/截图对比（黄金图像 + 显式容差阈值），
  或数值化帧统计（覆盖率、颜色/深度直方图、几何与 draw call 统计）。
- 仅凭肉眼确认的特性不得标记完成，不得合入主干。
- 视觉回归用例必须固定相机、时间、随机种子、视口尺寸与设备像素比；
  无法消除的非确定性来源必须量化并记录。
- 容差阈值必须写在测试代码中且可追溯来源；禁止"任意像素差异均通过"式的宽松判据。
- 视觉与数值断言必须覆盖两种后端：WebGL2 兜底路径与 WebGPU 路径各自独立运行并通过
  （独立会话、独立进程或独立用例，按原则 II 不得并发渲染同一场景）。

**Rationale**：GPU 渲染的失败模式通常是静默的（黑屏、丢三角形、颜色空间错位、
深度精度退化），只有自动化像素或数值断言能在 CI 中稳定捕获。

### IV. 性能以数据驱动（Data-Driven Performance）

- 任何优化必须由基准数据支撑：先提交基线，再提交优化；无基线对比的优化不予合入。
- 基准必须记录帧时间（frame time，至少 p50 与 p95）、GPU 显存占用与 draw call 数；
  指标口径与采集方法必须版本化并随仓库维护。
- 基准必须可复现：固定场景与数据集、固定 warm-up 与采样次数，硬件环境必须固定或明确标注。
- 性能回归门槛必须量化（例如帧时间或显存劣化超过既定阈值即判定失败）；
  阈值变更必须记录理由与影响。
- 优化提交必须附"基线 vs 优化后"的实测数据对比。
- 两条路径的基准 MUST 在各自独立的运行会话中采集，MUST NOT 以两条路径同时运行的会话作为对比口径。

**Rationale**：WebGPU 相对 WebGL2 的收益必须可证明；没有数字支撑的性能主张会掩盖真实的
架构成本与回归。以"仅一条路径运行"的会话采集基准，才能让数字反映后端本身而非并行开销。

### V. CI 为唯一事实来源（CI as the Single Source of Truth）

- 每次提交（含 PR）必须在 CI 中完成构建、测试与基准；三者任一未通过不得合入主干。
- 主干必须始终可构建、可运行、可回退；禁止合入使主干破损的提交。
- CI 产物（构建日志、测试报告、基准数据、视觉差异图）是判定"完成"的唯一权威依据；
  本地通过不等于通过。
- 必须维护与真实浏览器和 GPU 环境匹配的 CI 运行环境；若某类验证在 CI 中只能降级运行，
  该降级策略与其盲区必须显式记录，并规定本地复现步骤。
- fork 层改动必须纳入 CI 校验：补丁范围审计（原则 I）与升级演练的验证结果 MUST 作为 CI 产物存档。
- 开源交付所需的依赖与许可证检查纳入 CI。

**Rationale**：分布式协作与开源交付场景下，CI 是唯一人人可见、可复现、可审计的判定依据；
对受控 fork 而言，CI 还承担"补丁是否仍守住边界"的持续审计职责。

## 附加技术约束（Additional Constraints）

技术栈与交付形态：

- 语言：TypeScript（`strict` 模式开启）；构建：Rollup；产物：以 ESM 为主并附带类型声明。
- 运行时：Node.js >= 22（开发、构建与 CI 环境要求）。
- 集成形态：受控 fork —— 以 `@cesium/engine`（上游基线版本 1.145.0）为载体，改动隔离于渲染后端层；
  本项目自有代码（能力探测、路径选择、验证与基准基建）以独立包形式交付。
  MUST NOT 出现"上游源码拷贝后与上游脱钩"的无基线 fork：fork 必须保留与上游基线的可追溯关系
  与可 rebase 形态。
- 交付方式：开源项目，须包含 LICENSE、CONTRIBUTING、fork 基线与补丁范围说明，以及可复现构建说明；
  整体采用持续集成模式（无长期分支，短生命周期 PR 合入主干）。
- 首个里程碑（MVP）判据：跑通地形渲染 —— 在**同一上层 API**下可加载并渲染地形瓦片，
  WebGPU 路径运行一次（WebGL2 绘制不参与该次运行），WebGL2 兜底路径在独立运行中同样通过；
  两者均须通过可验证渲染断言（原则 III）与基准记录（原则 IV）。

## 测试与验证策略（Testing & Quality Gates）

- 分层测试：单元测试（纯 CPU 逻辑：抽象层契约、能力探测决策、参数校验）；
  契约测试（同一套用例参数化跑两种后端）；视觉回归测试（像素/截图对比）；基准测试（性能指标）。
- 双后端契约测试必须参数化执行：同一测试体在 WebGL2 与 WebGPU 上运行，且每次运行只启用一条路径
  （独立会话/独立进程/独立页面加载）；行为差异必须在测试中显式断言，禁止以条件跳过（skip）代替断言；
  禁止以"两条路径同时渲染同一场景"的方式取得对比数据。
- 逻辑层不改动（原则 I）MUST 由自动化证据支撑：补丁范围审计（改动文件清单必须全部位于渲染后端层）
  与升级（rebase）演练结果纳入 CI 产物。
- 视觉回归必须输出差异图（diff artifact）作为 CI 产物，以支持失败定位。
- 基准数据必须作为 CI 产物存档，形成历史序列以支持趋势判断。
- 质量门禁顺序：构建通过 → 单元与契约测试通过 → 视觉回归通过 → 基准不劣化 →
  fork 补丁范围审计通过 → 依赖与许可证检查通过；任一失败阻断合入。
- 跳过测试必须附理由并在 PR 中显式说明；禁止长期存在的无条件跳过。

## Governance

章程优先与合规校验：

- 本 constitution 优先于其他一切实践与约定；当章程与既有实践、模板或习惯冲突时，以章程为准。
- 所有 PR 与评审必须校验合规性：至少给出对应原则（I–V）的合规性说明，
  并列出验证证据路径（测试、基准数据、视觉差异产物、补丁范围审计与升级演练记录）。
- 违反原则的例外与额外复杂度必须在 plan 或 PR 中显式论证，
  并记录被否决的替代方案及理由。

修订流程（Amendment Procedure）：

- 修订提案必须以书面形式给出：变更内容、理由（Why）、影响范围（需调整的既有产物与代码）、
  迁移方案（Migration Plan）与生效日期。
- 修订须经维护者评审通过后方可合入。
- 原则 I 与原则 II 属 `NON-NEGOTIABLE`；其删除、放宽或重定义属破坏性治理变更，
  必须单独说明并给出完整迁移路径。
- 修订完成后必须更新 `Last Amended` 日期，并按语义化版本递增章程版本号。

版本策略（Versioning Policy）：

- 章程版本遵循语义化版本 MAJOR.MINOR.PATCH：
  - MAJOR：原则的删除、重定义，或向后不兼容的治理变更。
  - MINOR：新增原则或章节，或对既有条款的实质性扩展。
  - PATCH：措辞澄清、错别字修正等非语义性调整。
- 版本变更记录于 `Last Amended` 与提交信息中（例如 `docs: amend constitution to vX.Y.Z`）。

本次修订记录（v1.0.0 → v2.0.0，Amendment Rationale）：

- **触发原因（用户澄清的真实意图）**："我需要的时候使用 WebGPU 管线替换 WebGL2，要求是这样的，
  而不是什么双层或者一起运行。还有我需要的是只替换管线，其他的逻辑都不能变，那管线完成之后，
  其他自然而然的就接入了。"
- **v1.0.0 的偏差**：v1.0.0 的原则 I 要求"绝不 fork 上游"，而渲染后端替换在上游公开接缝处不可行
  （`Scene.context` 为 `@private`，上游不支持注入外部画布/上下文）；该禁令会迫使实现转向
  "双画布分层 + 把上游那次地形绘制藏起来"的旁路方案——即两套管线并行绘制同一场景，
  既付双份开销，又使影像/模型/大气等既有功能永远无法接入。该方案已被用户明确否决。
- **本次修订内容**：原则 I 由"绝不 fork"改为"受控 fork 但严格局限在渲染后端层"；
  原则 II 由"渐进式接管"改为"二选一、不同时运行"，并显式禁止共存、分层与遮挡式实现；
  原则 III/IV/V 与附加技术约束、测试与验证策略按新架构同步措辞。
- **影响范围**：`specs/001-webgpu-terrain-mvp/` 下的需求与方案产物需同步修订
  （Dependencies 的 fork 表述、双路径一致性 FR 的"二选一"语义、新增"管线替换"FR）；
  v1.0.0 下已产出的 plan 与 research 中"双画布分层"相关决策 MUST 作废并重写。
- **迁移方案**：规格（spec）先对齐；随后整体重写 plan / research / data-model / contracts / tasks，
  使全部设计决策落在"渲染后端替换"这一路径上；v1.0.0 遗留的"双画布分层"方案不得作为退路保留。
