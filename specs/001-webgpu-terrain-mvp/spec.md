# Feature Specification: WebGPU Terrain Rendering MVP

**Feature Branch**: `001-webgpu-terrain-mvp`

**Created**: 2026-09-18

**Status**: Draft

**Input**: User description: "新增产品需求：CesiumJS 的新增 WebGPU 渲染管线。1、基于 CesiumJS 现有最新稳定版本（1.145.0）。2、加入 WebGPU 管线，实现和优化 CesiumJS 现有的功能。整体采用持续集成模式运行。我需要知道最小 MVP（跑通地形渲染）的时间和花销。技术要求：建议使用 CesiumJS 外置模块的形式来集成 CesiumJS；本项目使用 TypeScript + Rollup；本项目采用开源项目方式搭建，仓库 git@github.com:yudhcq/Cesiumjs-WebGPU.git"

**Scope note**: 本条规格只覆盖**首个增量（MVP）：把地形渲染端到端跑通**。「用 WebGPU 实现并优化 CesiumJS 现有全部功能」是产品愿景，属于 Out of Scope，由后续增量承接。

## Clarifications

### Session 2026-09-18

- Q1: MVP 的时间/花销评估必须以什么为计量基准？ → A: 花销只按 **AI/Agent 消耗**计量，即模型 token 消耗（输入与输出分别计量）加算力费用；**人工成本不单独计价**，且该口径必须在评估结论中显式声明。时间仍以区间表示。
- Q2: 地形数据源是否必须支持需要凭据的专业地形服务？ → A: 不必须。MVP 只使用**免登录、公开可访问**的地形数据，并以**本地固定数据集**保证离线与确定性；Cesium ion 等需要访问令牌（凭据）的专业地形服务后置到后续增量。
- Q3: MVP 是否设置硬性交付期限（例如 30 个日历日）？ → A: **不设硬性交付期限**。交付时给出可追溯的时间区间与偏差说明；超出该区间时以书面形式说明偏差原因与新预期。
- Q4: constitution v1.0.0 是否需要在本增量修改？ → A: **不需要**。constitution v1.0.0 已获批准，本增量不改动，作为既定原则约束后续阶段。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 地形渲染在新渲染路径下端到端跑通 (Priority: P1)

项目使用者（集成本项目的应用开发者）在浏览器中打开随仓库提供的演示页面，场景中相机对准一片真实地形区域，地形瓦片被加载并以正确的起伏、光照与遮挡关系呈现出来；用户可以用鼠标缩放、旋转、平移，画面随之连续更新。整个过程由"新渲染路径"完成，而不是旧渲染路径。

**Why this priority**: 这是整个产品的前提假设——如果地形无法在新渲染路径下端到端呈现，后续任何"实现并优化现有功能"的工作都没有立足点。它同时也是本项目对外可演示、可评估的最小价值单元。

**Independent Test**: 在只启用新渲染路径的浏览器中加载固定演示场景（固定相机位置、朝向、视口尺寸、时刻与像素比），地形被渲染出来并通过自动化视觉/数值断言，即视为通过。不依赖其他用户故事。

**Acceptance Scenarios**:

1. **Given** 一个支持新渲染路径的桌面浏览器与可用的地形数据，**When** 用户加载演示场景并等待瓦片就绪，**Then** 地形以连续表面呈现（非空白、非纯背景色），且可见起伏与该区域真实高程分布一致。
2. **Given** 地形已渲染完成且相机固定，**When** 采集该帧，**Then** 画面与已批准参考帧在声明的容差内一致，且帧统计（非背景像素占比、颜色/深度分布）落在声明区间内。
3. **Given** 地形已渲染完成，**When** 用户拖拽旋转或滚轮缩放，**Then** 画面在交互过程中持续更新且地形保持几何正确（无撕裂、无空洞、无瓦片跳变），交互过程中不出现超过 1 秒的连续卡顿。
4. **Given** GPU 在会话中途不可用（设备丢失），**When** 系统恢复渲染，**Then** 场景自动恢复到可交互状态，无需用户手动刷新页面。

### User Story 2 - 新路径不可用时旧路径必须兜底 (Priority: P1)

使用者在只有旧渲染路径可用的浏览器（或不具备所需 GPU 能力的设备）上打开同一个演示页面，场景依然正常渲染地形并可交互；用户不需要改代码、不需要切换开关，也不会看到错误页或黑屏。开发者也可以显式指定使用哪条路径，用于对比与排查。

**Why this priority**: 与 P1 同级。地形渲染本身是 MVP 的价值，而"任何设备都能跑"是本项目对外承诺的底线；没有兜底，新路径一旦在真实设备上不可用，整个产品就退化为不可用状态。

**Independent Test**: 在同一次测试运行中，同一套断言用例分别在两条渲染路径下执行并通过；将新路径强制置为不可用后，页面仍渲染出通过断言的地形，且调用方代码无需任何分支改动。

**Acceptance Scenarios**:

1. **Given** 浏览器不支持新渲染路径，**When** 加载演示场景，**Then** 场景通过兜底路径渲染出地形，并给出"当前使用兜底路径"的可观察提示（如状态文案/控制台信息）。
2. **Given** 新渲染路径的能力探测失败或用时超限，**When** 系统决定渲染路径，**Then** 系统在可接受的等待时间内（不超过 2 秒）自动改用兜底路径，且不抛出未捕获错误、不阻塞页面其余部分。
3. **Given** 集成方把渲染路径配置为兜底路径，**When** 加载场景，**Then** 渲染完全走兜底路径，且集成方代码中不出现任何"当前是哪条路径"的条件分支。
4. **Given** 同一场景在两条路径下渲染，**When** 对比两帧，**Then** 视觉差异在声明的容差内，且场景语义（可见地形范围、相机行为、时间推进）一致。

### User Story 3 - 渲染结果可自动化验证 (Priority: P2)

维护者在提交代码后，由流水线自动判定"地形渲染是否正确"，并给出可下载的差异证据；维护者不需要在本机肉眼观察，也不需要人工比对截图。任何"我觉得看起来对"的结论都不足以让改动合入。

**Why this priority**: 渲染故障通常是静默的（黑屏、丢三角形、颜色空间错位、深度精度退化），只有自动化断言能在每次提交上稳定捕获；这也是本项目长期开放协作、可回退的前提。

**Independent Test**: 在流水线中运行渲染验证任务，产出通过/失败结论与差异证据文件；人为引入一处渲染缺陷后，验证任务必须失败并指出差异区域。

**Acceptance Scenarios**:

1. **Given** 一次代码提交，**When** 流水线运行渲染验证，**Then** 两条渲染路径的用例都被执行，任一路径未通过即判定本次提交失败。
2. **Given** 渲染验证失败，**When** 维护者查看流水线产物，**Then** 能找到差异图与统计数值，定位到差异所在区域与幅度。
3. **Given** 参考帧需要更新（有意的视觉变更），**When** 提交更新参考帧，**Then** 更新必须经过评审并在提交信息中说明原因，且旧参考帧的变更历史可追溯。
4. **Given** 验证依赖固定条件（相机、时间、视口、像素比、数据源），**When** 同一提交重复运行验证，**Then** 结论稳定一致，不出现随机通过/失败。

---

### User Story 4 - 性能结论由数据支撑 (Priority: P2)

维护者在合入任何"优化"前，能拿到可比较的性能数据：新路径与旧路径在同一固定场景下的帧时间分布、显存占用与绘制批次数量；优化前后各有一次记录，劣化超过既定门槛时流水线直接失败。

**Why this priority**: 新产品线相对旧路径的收益必须被证明；没有数字支撑的性能主张会把架构代价与回归掩盖掉。

**Independent Test**: 在流水线中运行基准任务，产出结构化基准数据（含环境标注）；人为引入一处性能劣化后，基准门槛判定失败。

**Acceptance Scenarios**:

1. **Given** 一次代码提交，**When** 流水线运行基准，**Then** 产出帧时间（中位数与尾部）、显存占用、绘制批次数三项指标，并标注运行环境。
2. **Given** 已有基线数据，**When** 新提交的指标劣化超过既定门槛，**Then** 流水线判定失败并给出与基线的差值。
3. **Given** 一次性能优化提交，**When** 提交被评审，**Then** 提交内容包含"优化前 vs 优化后"的实测对比数据。
4. **Given** 某次基准在受限环境（无真实 GPU）中降级运行，**When** 结果被引用，**Then** 降级方式与其盲区在记录中显式标注，并附本机复现步骤。

---

### User Story 5 - 拿到 MVP 的工期与 AI/Agent 消耗结论 (Priority: P2)

项目决策者（出资方/产品负责人）在首个增量交付时，拿到一份可直接用于排期与预算的结论：达到"地形渲染跑通"这一里程碑需要多少时间（区间）、AI/Agent 消耗多少（模型 token 量与算力费用区间），按工作流拆分，并注明计量口径与前提。该结论还要能被后续增量复用为估算基线。

**Why this priority**: 用户明确要求"MVP 的时间和花销"，按已确认口径即时间区间加 AI/Agent 消耗（token 与算力）区间，这是本增量最直接的交付价值之一；没有它，无法排期，也无法决策。

**Independent Test**: 检查已发布的评估文档，逐项核对是否覆盖全部工作流、是否给出时间区间与 AI/Agent 消耗区间（模型 token 量与算力费用）、是否标注计量口径（只计 AI/Agent 消耗、人工成本不计入并显式声明）与前提；对照实际交付记录验证偏差是否被说明。

**Acceptance Scenarios**:

1. **Given** 首个增量交付，**When** 决策者查阅交付物，**Then** 存在一份评估结论，包含：达到"MVP 地形渲染跑通"所需的时间区间、AI/Agent 消耗区间（模型 token 量区间 + 算力费用金额区间），并按工作流拆分。
2. **Given** 评估结论已发布，**When** 决策者阅读，**Then** 结论显式写明计量口径（token 计量方式：输入/输出分别计量；模型与算力单价来源；是否含流水线与云 GPU 资源；货币单位；执行环境与并行度假设）与全部前提假设，并显式声明"人工成本不计入"。
3. **Given** 首个增量实际交付完成，**When** 复核评估结论，**Then** 实际所用时间与 AI/Agent 实际消耗被记录，与估算区间的偏差被说明，并作为后续增量的估算基线。
4. **Given** 评估结论中的单项估算，**When** 决策者审阅，**Then** 每项都能追溯到具体工作流与其消耗驱动因素（如瓦片加载与调度、地形绘制实现、验证资产建设、流水线搭建）。

### Edge Cases

- **浏览器完全没有新渲染路径**：不得报错或黑屏，自动走兜底路径并给出可观察提示。
- **新渲染路径存在但设备请求失败**（驱动黑名单、隐私设置、远程桌面、虚拟机）：探测与自动回退必须在 2 秒内完成，且失败原因可观察。
- **会话中途设备丢失或设备挂起**：恢复后场景可继续交互，状态提示用户；不得出现永久黑屏或未捕获错误。
- **地形瓦片获取失败或超时**：展示"数据不可用"的可观察状态，其余瓦片继续渲染；不得导致整帧丢弃或页面卡死。
- **地形服务返回空瓦片/无效瓦片**：按"无数据"处理，不产生错误几何（不出现尖刺、穿模、NaN 顶点）。
- **设备能力处于下限**（低显存、最大纹理尺寸小、纹理格式受限）：以已声明的能力下限为界，低于下限时归入"不支持新路径"并走兜底路径。
- **超出一块瓦片覆盖范围或跨越瓦片接缝**：相邻瓦片高程衔接连续，接缝处不出现可见裂缝或错位。
- **无网络或离线运行**：固定演示数据在离线环境下仍可完成验证（验证不得依赖实时网络）。
- **重复运行的确定性**：同一提交在相同固定条件下重复运行得到一致结论；无法消除的非确定性来源被量化并记录。
- **固定相机下仅覆盖单块瓦片**：验证用例必须至少覆盖多瓦片拼接场景，避免"单瓦片通过即整体通过"的假阳性。

## Requirements *(mandatory)*

### Functional Requirements

**A. 地形渲染能力（新渲染路径）**

- **FR-001**: 系统 MUST 在浏览器环境中通过新渲染路径渲染地形，产出连续地形表面；"连续"指：相机固定时画面非空白、非纯背景色，且可见高程起伏与数据源真实高程分布一致。
- **FR-002**: 系统 MUST 支持对地形场景的相机交互（缩放、旋转、平移），交互过程中地形几何保持正确（无撕裂、空洞、错误遮挡），且单次交互不产生超过 1 秒的连续卡顿。
- **FR-003**: 系统 MUST 在会话中途渲染设备不可用（设备丢失）后恢复到可交互状态，恢复过程无需用户刷新页面，且产生可观察的状态提示。
- **FR-004**: 系统 MUST 从地形数据来源加载地形瓦片，并以可观察方式区分"数据不可用"与"渲染失败"两种状态。MVP 的数据源 MUST 为**免登录、公开可访问**的地形数据，并 MUST 附带**本地固定数据集**以保证离线与确定性；需要凭据（访问令牌）的专业地形服务 MUST NOT 成为 MVP 的任何前置依赖，仅可在后续增量中按需接入。

**B. 双路径一致性与兜底（渐进接管）**

- **FR-005**: 系统 MUST 在新渲染路径之前完成能力探测（新路径可用性、设备可用性、必需能力项与下限），探测失败、超时（上限 2 秒）或能力不足时 MUST 自动改用兜底渲染路径，且不抛出未捕获错误、不阻塞页面。
- **FR-006**: 系统 MUST 保证兜底渲染路径在任何时刻都是可用的默认路径；新路径在任何情况下都不得成为唯一可运行路径。
- **FR-007**: 系统 MUST 使集成方能够以配置方式（构建期或运行时）选择渲染路径，且集成方代码中 MUST NOT 出现渲染路径的条件分支，也 MUST NOT 直接引用具体路径的类型。
- **FR-008**: 系统 MUST 对同一场景在两条路径下提供一致的上层行为与视觉语义：在声明的容差内视觉等价；无法消除的差异 MUST 在契约中显式声明，并附断言。
- **FR-009**: 当系统自动回退到兜底路径时，MUST 产出可观察的提示（对使用者可见的状态信息或对维护者可见的运行日志），说明"已使用兜底路径"及原因类别。

**C. 可验证渲染**

- **FR-010**: 每项渲染特性 MUST 附带自动化验证，形式为像素/截图对比（含显式容差阈值）或数值化帧统计（非背景覆盖率、颜色/深度分布、几何与绘制请求统计）；仅凭肉眼确认的特性 MUST NOT 标记为完成。
- **FR-011**: 验证 MUST 在两条渲染路径上分别执行；任一路径未通过即判定该次提交失败。
- **FR-012**: 验证 MUST 固定相机、场景时间、随机种子、视口尺寸与设备像素比，并固定地形数据集；无法消除的非确定性来源 MUST 被量化并记录。
- **FR-013**: 验证失败时 MUST 产出差异证据（差异图与统计数值），并作为流水线产物保存，供维护者定位。
- **FR-014**: 容差阈值 MUST 可追溯（来源与理由被记录）；系统 MUST NOT 采用"任意像素差异均通过"式的宽松判据。
- **FR-015**: 验证用例 MUST 覆盖多瓦片拼接场景，且 MUST 覆盖兜底路径本身（兜底路径必须有测试覆盖）。
- **FR-016**: 几何类缺陷（瓦片接缝裂缝、空洞、错误遮挡、异常顶点）MUST 由数值化断言捕获（如覆盖率突变、深度不连续处的像素比例、几何统计超出区间），MUST NOT 依赖人工目视判断。

**D. 性能与数据驱动**

- **FR-017**: 系统 MUST 提供可复现的基准，记录帧时间（至少中位数与尾部 p95）、图形内存占用与场景提交给图形接口的绘制请求次数；基准 MUST 固定场景与数据集、固定预热与采样次数，并标注硬件与软件环境。
- **FR-018**: 系统 MUST 定义量化的性能回归门槛（例如帧时间或图形内存占用劣化超过既定百分比即判定失败），门槛变更 MUST 记录理由与影响。
- **FR-019**: 任何性能优化 MUST 先提供基线数据，并在提交中附"基线 vs 优化后"的实测对比；无基线对比的优化 MUST NOT 合入。
- **FR-020**: 基准数据 MUST 作为流水线产物存档，形成可比较的历史序列。

**E. 持续集成与交付事实来源**

- **FR-021**: 每次提交（含变更请求）MUST 在持续集成中完成构建、测试与基准；三者任一未通过 MUST NOT 合入主干。
- **FR-022**: 判定"完成"的权威依据 MUST 是流水线产物（构建日志、测试报告、基准数据、视觉差异产物）；本地通过 MUST NOT 视为通过。
- **FR-023**: 若某类验证在流水线环境中只能降级运行（例如无真实 GPU），该降级策略与其盲区 MUST 显式记录，并给出本地复现步骤。
- **FR-024**: 交付 MUST 为开源形态，包含许可证、贡献指南与可复现构建说明；依赖与许可证检查 MUST 纳入流水线。
- **FR-025**: 主干 MUST 始终可构建、可运行、可回退；不得合入使主干破损的提交。

**F. MVP 工期与 AI/Agent 消耗评估（本增量的交付物）**

- **FR-026**: 首个增量交付时，MUST 同时产出一份 MVP 工期与 AI/Agent 消耗评估结论，覆盖"地形渲染跑通"这一里程碑，并按工作流拆分（至少包含：渲染管线与地形绘制、双路径能力探测与兜底、验证资产与测试基建、持续集成与基准基建、开源交付与文档）。
- **FR-027**: 评估结论 MUST 以时间区间与 AI/Agent 消耗区间表示，并显式写明计量口径与前提。消耗区间只计 AI/Agent 消耗，即模型 token 消耗与算力费用；口径项 MUST 至少包含：token 计量方式（输入/输出分别计量）、模型与算力单价来源、是否含流水线与云 GPU 资源、货币单位、执行环境与并行度假设。**人工成本 MUST NOT 计入消耗区间，且评估结论中 MUST 显式声明该口径**。
- **FR-028**: 评估结论 MUST 随仓库版本化发布，可被评审与后续修订；后续增量 MUST 复用该结论作为估算基线，并在首个增量实际交付后记录实际时间与 AI/Agent 实际消耗值，以及其与估算区间的偏差及原因。
- **FR-029**: 评估结论 MUST 明确区分"已确认的消耗项"与"待确认的消耗项"（如云 GPU 算力的实际报价、模型单价的变动），待确认项 MUST 标注其对结论区间的影响方向与幅度量级。凭据类地形服务已明确后置到后续增量，MUST NOT 作为本增量的消耗项计入。

### Key Entities *(include if feature involves data)*

- **地形瓦片（Terrain Tile）**：按空间层级与网格位置标识的一段地形表面数据，含高程信息与瓦片层级/边界标识；瓦片之间存在父子与邻接关系；存在"有数据/无数据/获取失败"三种可取状态。
- **渲染路径（Render Path）**：一组可被选择的绘制实现，对使用者表现为同一能力。属性：标识、是否被选择、不可用原因类别（不支持/探测失败/能力不足/设备丢失）。
- **能力探测结果（Capability Probe Result）**：一次探测的结论。属性：新路径是否可用、设备是否获取成功、能力项与下限是否满足、探测耗时、失败原因类别。
- **视觉验证证据（Visual Verification Evidence）**：一次验证运行的产物。属性：运行路径标识、固定条件快照（相机/时间/视口/像素比/数据集）、采集帧、与参考帧的差异图、统计数值、容差阈值与结论。
- **基准记录（Benchmark Record）**：一次基准运行的产物。属性：提交标识、环境标注（硬件/软件/是否降级运行）、帧时间中位数与 p95、显存占用、绘制批次数、是否通过回归门槛。
- **MVP 评估结论（MVP Estimate）**：一份版本化的工期与 AI/Agent 消耗结论。属性：里程碑定义、工作流拆分项、每项时间区间与 AI/Agent 消耗区间（模型 token 量 + 算力费用）、计量口径（只计 AI/Agent 消耗，人工成本不计入并显式声明）、货币单位（人民币并同时给出美元口径）、前提假设、已确认/待确认消耗项、后续增量基线引用。
- **验证数据集（Verification Dataset）**：固定用于渲染验证与基准的地形数据与相机配置集合，保证跨运行、跨提交可比。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 首次增量内，固定演示场景在两条渲染路径下都能在一次连续运行中完成地形渲染并各自通过自动化断言（零未捕获错误、零人工肉眼确认）；断言对**多瓦片拼接**场景成立。
- **SC-002**: 在固定相机下，渲染结果与该地形区域的高程特征一致：高程最高与最低处的可观察表现差异明显（如明暗或遮挡差异），且不出现空白、纯背景色或整片单色区域——由自动化统计断言判定，而非人工观察。
- **SC-003**: 在不支持新渲染路径的浏览器中，同一场景仍能完成地形渲染，自动回退在 2 秒内完成，且页面不出现错误提示或空白画面。
- **SC-004**: 地形初步就绪后，连续 3 秒内的交互（旋转、缩放、平移）过程中，单次交互无超过 1 秒的连续卡顿，全过程无未捕获错误；交互结束后的定格帧仍满足 SC-001 与 SC-002 的自动化断言（即交互未引入几何破坏）。
- **SC-005**: 流水线在每次提交上同时运行两条路径的验证与基准任务，从提交到结论的总耗时不超过 20 分钟；任一失败即阻断合入。
- **SC-006**: 存在一次可比较的基准记录，含帧时间中位数与 p95、图形内存占用、绘制请求次数，并在同一环境下对新路径与兜底路径各采集至少一次；后续提交可自动判定是否劣化超过既定门槛。
- **SC-007**: 首个增量交付时，同时交付一份 MVP 工期与 AI/Agent 消耗评估结论：给出达到"地形渲染跑通"里程碑的时间区间，以及 AI/Agent 消耗区间（模型 token 量 + 算力费用），按工作流拆分；并写明计量口径——只计 AI/Agent 消耗（token 计量方式为输入/输出分别计量，含单价来源与执行环境假设），**人工成本不计入且 MUST 显式声明该口径**；货币为人民币并同时给出美元口径。
- **SC-008**: 本增量**不设硬性交付期限**；交付时 MUST 给出可追溯的时间区间与偏差说明（覆盖"可演示地形渲染 + 双路径验证通过 + 首份基准记录 + 工期与 AI/Agent 消耗评估结论"四项齐备），实际用时超出该区间时 MUST 书面说明偏差原因与新预期。
- **SC-009**: 任何渲染改动在合入前都附带可追溯的验证证据（差异图或统计数值）与容差来源说明；对已合入提交的抽查中，缺失证据的比例为 0。

### Out of Scope（本增量不做）

- 用新渲染路径实现 CesiumJS 现有**全部**功能的平移与优化（产品愿景，后续增量）：三维瓦片、glTF/模型、影像图层、大气与光照特效、阴影、后处理、粒子、矢量与标注等一律不在本增量。
- 面向生产的数据规模与流式调度优化（海量瓦片、预取策略、磁盘缓存策略调优）。
- 移动端与低端设备的适配与性能调优。
- 凭据类/商业地形服务的接入（已确认后置到后续增量）。
- 多浏览器全矩阵兼容（新渲染路径的最低浏览器基线由 Dependencies 段定义）。
- 用新渲染路径实现通用计算加速（模拟、地形生成、后处理链等）。
- 新增上游不存在的渲染特性（本增量只覆盖"地形渲染"这一既有能力在新路径下的等价实现）。
- 发布到包管理器的正式版本号与语义化发布节奏（本增量只要求开源形态与可复现构建）。

## Dependencies

- **上游渲染库**：CesiumJS 1.145.0（当前稳定版）作为对等依赖（peer dependency）引入，**不 fork、不 vendor、不打补丁**；一切扩展只经上游公开 API 与官方扩展点完成。上游基线升级必须在只改适配层的前提下通过既有全量验证。
- **集成形态**：以外部模块（独立软件包 + 可选插件注册）形式集成，不修改上游源码。
- **语言与构建**：TypeScript（`strict` 模式）作为实现语言，Rollup 作为构建工具，产物以 ES 模块为主并附带类型声明。
- **运行时环境**：Node.js >= 22（开发、构建与持续集成环境）。
- **交付与协作**：开源仓库 `git@github.com:yudhcq/Cesiumjs-WebGPU.git`（当前为空仓库）；整体采用持续集成模式（无长期分支，短生命周期变更请求合入主干）。
- **地形数据源（已确定）**：MVP 使用免登录、可公开访问的地形瓦片服务或本地打包的固定地形数据集（见 FR-004 与 Assumptions）。Cesium ion 等需要访问令牌（凭据）的专业地形服务**不属于本增量依赖**，属后续增量按需接入；因此持续集成与验证 MUST 在无任何凭据的前提下可运行，联网不可用或服务不可用时 MUST 能以本地固定数据集完成验证与基准。
- **浏览器环境**：新渲染路径仅在较新版本的桌面浏览器中可用；兜底路径面向既有主流浏览器。持续集成环境的浏览器与图形栈需满足此前提，否则按 FR-023 记录降级策略。
- **既有验证资产**：参考帧、容差阈值与固定数据集由本增量新建（仓库当前无任何提交）。

## Assumptions

- **目标用户**：直接使用者是集成本项目的应用开发者与仓库维护者；间接受益者是使用这些应用的终端用户。MVP 面向桌面浏览器。
- **运行环境假设**：终端用户使用较新版本的桌面浏览器；不支持新渲染路径的浏览器按兜底路径处理，属受支持场景而非故障。
- **数据源选择（已确认）**：MVP 采用**免登录、公开可访问**的地形数据（公开地形瓦片服务，或本地打包的固定地形数据集以保证离线与确定性）。需要凭据的专业地形服务**不是 MVP 的必需项**，后置到后续增量。
- **验证确定性**：默认以固定数据集 + 固定相机/时间/视口/像素比达成确定性；持续集成默认无真实 GPU，采用软件光栅化或受限图形栈运行，其盲区按 FR-023 记录。
- **成本口径（已确认）**：花销只按 **AI/Agent 消耗**计量，即模型 token 消耗（输入与输出分别计量）加算力费用；货币为人民币并同时给出美元口径；消耗区间包含持续集成与云 GPU 等算力资源费用，不含任何商业地形服务订阅费用（因 MVP 只用免登录数据源）。**人工成本不单独计价，且 MUST 在评估结论中显式声明该口径**；时间仍以区间表示。
- **执行方式与并行度**：MVP 由 **Agent 工作流**执行，人工只承担审批与验收（需求确认、产物审阅、合入决策），不计入实现工时；工期区间与 AI/Agent 消耗区间均按该执行方式成立。若改为人工实现，或人工参与程度与并行度发生变化，MUST 重新评估并修订结论。
- **上游能力边界**：地形加载、瓦片调度、相机模型与场景时间推进复用上游既有公开能力，本增量只新增"绘制执行"这一环节；因此不在本增量重新设计地形数据格式或空间索引。
- **等价性定义**：默认采用"固定条件下像素差异在不含抗锯齿边缘的区域内、于声明容差内一致"作为视觉等价的可测定义；精确阈值在方案阶段确定并记录来源。
- **性能期望**：MVP 的首要目标是**正确性与可验证性**，其次是相对兜底路径不劣化；绝对性能提升目标不作为首个增量的成功判据，避免在数据不足时给出无依据的性能承诺。
- **许可证与合规**：假定采用对开源友好的许可证（具体选型在方案阶段确定），并纳入流水线检查。
- **估算结论的时效**：MVP 评估结论基于当前已知范围；范围或执行条件变更（澄清结果、数据源变化、执行方式或并行度变化、模型与算力单价变化）必须触发结论修订并说明差异。
